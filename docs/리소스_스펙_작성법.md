# 리소스 스펙 작성 규칙

## 1. 기본 원칙

* 하나의 스펙은 하나의 리소스만 다룬다.
* 리소스가 직접 발생시키는 규칙만 기록한다.
* 다른 리소스가 규칙의 주체인 경우 해당 리소스의 스펙에 기록한다.
* 스펙에 명시된 동작·상태·관계만 존재하는 것으로 간주한다.
* 비명시 사항을 설명하기 위한 부정문은 작성하지 않는다.
* 코드 구현 방식과 내부 처리 로직은 작성하지 않는다.
* 식별을 위한 키값은 작성할 수 있다.
* 처리 순서나 시스템 내부 우선순위는 작성하지 않는다.
* 설명보다 표와 참조를 우선한다.
* 하나의 사실을 여러 위치에 중복 작성하지 않는다.

## 2. 문서 구조

각 리소스는 다음 순서로 작성한다.

1. 기본 정보
2. 상태
3. 동작
4. 관계
5. 사운드
6. 시각 표현
7. 프리뷰
8. 참조
9. 규칙 근거

해당 리소스에 필요한 항목만 사용한다.

내용이 없는 섹션은 생성하지 않는다.

## 3. 기본 정보

리소스를 식별하는 최소 정보를 기록한다.

| 항목     | 작성 기준              |
| ------ | ------------------ |
| 블록명    | 게임 내 공식 명칭         |
| 식별자    | 문서 내 참조용 고유 ID     |
| 키      | 리소스 또는 데이터 식별 키    |
| 분류     | 오브젝트 / 필드 / 컨트롤 등  |
| 블록 이미지 | 실제 이미지 또는 빈칸       |
| 핵심 속성  | 해당 리소스를 정의하는 고정 속성 |

리소스의 기능 설명은 한 문장으로 제한한다.

## 4. 상태

실제로 존재하는 상태만 정의한다.

| 상태  | 키       | 조건             |
| --- | ------- | -------------- |
| 상태명 | 상태 식별 키 | 해당 상태가 성립하는 조건 |

상태는 다음 기준을 만족해야 한다.

* 게임 규칙상 구분되는 상태여야 한다.
* 시각적 표현만 다른 경우 별도 상태로 만들지 않는다.
* 일시적인 연출과 논리 상태를 혼합하지 않는다.
* 상태 이름은 동일한 개념을 일관되게 사용한다.

## 5. 동작

해당 리소스가 직접 발생시키는 동작만 기록한다.

| 조건 또는 이벤트 | 동작      | 결과         |
| --------- | ------- | ---------- |
| 발생 조건     | 수행되는 규칙 | 직접 발생하는 결과 |

동작 작성 시 다음을 포함한다.

* 동작 발생 조건
* 직접 변경되는 값
* 위치 변화
* 소유권 변화
* 상태 변화

다른 리소스가 이후에 수행하는 결과는 기록하지 않는다.

## 6. 관계

해당 리소스가 직접 규칙을 발생시키는 대상과의 관계만 기록한다.

| 대상     | 관계   | 결과                |
| ------ | ---- | ----------------- |
| 참조 리소스 | 관계 키 | 해당 관계로 직접 발생하는 결과 |

관계는 방향성을 가진다.

예:

`A → B`

A의 규칙 때문에 B와의 관계가 발생하면 A에 기록한다.

B의 규칙 때문에 관계가 발생하면 B에 기록한다.

양쪽 모두 독립적인 규칙을 가지고 있다면 각각의 스펙에 각자의 규칙만 기록한다.

## 7. 소유권

소유권이 해당 리소스의 핵심 규칙인 경우에만 작성한다.

다음 정보를 명확히 한다.

| 항목    | 작성 내용              |
| ----- | ------------------ |
| 소유 대상 | 무엇을 소유하는가          |
| 보유 범위 | 최소 / 최대 보유량        |
| 획득    | 어떤 조건에서 소유하게 되는가   |
| 전달    | 어떤 조건에서 소유권이 이동하는가 |
| 교환    | 어떤 단위로 교환되는가       |

소유권의 생성·삭제·변환 여부는 실제 규칙으로 존재할 때만 기록한다.

## 8. 사운드

사운드는 이벤트 기준으로 정의한다.

| 이벤트  | 키     | 발생 조건    |
| ---- | ----- | -------- |
| 이벤트명 | 사운드 키 | 실제 재생 조건 |

필요한 경우 다음을 추가한다.

* 충돌 사운드
* 이동 사운드
* 상호작용 사운드
* 상태 변경 사운드
* 소유권 전달 사운드
* 활성화 / 비활성화 사운드
* 성공 / 실패 사운드

하나의 이벤트에 여러 사운드가 필요한 경우 각각 별도 항목으로 정의한다.

## 9. 시각 표현

논리 상태와 이벤트가 화면에서 어떻게 표현되는지 정의한다.

| 상태 또는 이벤트 | 표현            |
| --------- | ------------- |
| 상태명       | 지속적으로 보여주는 표현 |
| 이벤트명      | 전환 또는 순간 연출   |

다음 요소를 사용할 수 있다.

* 블록 이미지
* 상태 이미지
* 애니메이션
* 색상
* 아이콘
* 강조
* 연결선
* 이펙트

현재 상태는 순간 연출이 종료된 뒤에도 식별 가능해야 하는 경우 이를 명시한다.

## 10. 프리뷰

스토리북에서 독립적으로 확인해야 하는 대표 사례를 정의한다.

| 프리뷰 | 참조          |
| --- | ----------- |
| 이름  | 상태 또는 관계 참조 |

프리뷰는 다음 기준으로 선정한다.

* 기본 상태
* 주요 상태 변화
* 핵심 동작
* 핵심 관계
* 소유권 변화
* 사운드가 발생하는 대표 이벤트

프리뷰 이름은 짧고 일관된 형식을 사용한다.

예:

* `Default`
* `Active`
* `Move`
* `Transfer`
* `Collision / Wall`
* `State / Active`

## 11. 참조

다른 리소스를 직접 설명하지 않고 참조 ID만 제공한다.

예:

* `OBJ-NORMAL` — 일반 오브젝트
* `FIELD-PLATE` — 플레이트
* `CTRL-RIGHT` — 오른쪽 컨트롤

웹 구현 시 참조는 해당 리소스 페이지로 이동하는 링크가 된다.

## 12. 규칙 근거

확정된 게임 규칙의 출처를 기록한다.

예:

* 룰북 § Object Reference
* 룰북 § Field Reference
* 룰북 § Ownership Transfer

규칙 근거에 없는 내용을 스펙에서 임의로 확정하지 않는다.

기획상 새로 결정한 내용이 필요한 경우 먼저 원본 규칙에 반영한 후 리소스 스펙에 작성한다.

## 13. 문장 규칙

문장은 사실 중심으로 작성한다.

권장:

* `일반 오브젝트가 점유하면 활성 상태가 된다.`
* `사용한 컨트롤을 상대 일반 오브젝트에게 전달한다.`
* `활성화 시 sfx.field.plate.activate를 재생한다.`

피한다:

* `다른 오브젝트는 영향을 주지 않는다.`
* `이 기능은 사용할 수 없다.`
* `필요에 따라 처리한다.`
* `관련 규칙에 따라 동작한다.`
* `적절한 사운드를 재생한다.`

모든 문장은 가능한 한 **조건 → 동작 → 결과**가 명확해야 한다.

## 14. 웹 리소스북 기준

각 스펙은 차후 self-contained HTML 리소스북에서 하나의 독립 페이지 또는 섹션으로 표현할 수 있어야 한다.

구성 요소는 다음 역할을 가진다.

| 요소    | 웹 표현            |
| ----- | --------------- |
| 식별자   | 페이지 제목 / 앵커     |
| 키     | 코드 스타일 텍스트 + 복사 |
| 기본 정보 | 요약 테이블          |
| 상태    | 상태 테이블          |
| 동작    | 동작 테이블          |
| 관계    | 참조 링크 테이블       |
| 사운드   | 이벤트 테이블         |
| 시각 표현 | 프리뷰 설명          |
| 프리뷰   | Story 단위        |
| 참조    | 내부 링크           |
| 규칙 근거 | 출처 링크           |

리소스 간 설명을 중복하지 않고 참조를 통해 연결한다.

## 15. 최종 검수

스펙 작성 후 다음을 확인한다.

* [ ] 하나의 리소스만 다루고 있는가
* [ ] 해당 리소스가 직접 발생시키는 규칙만 포함했는가
* [ ] 상대 리소스의 규칙을 대신 설명하고 있지 않은가
* [ ] 명시되지 않은 사실을 부정문으로 추가하지 않았는가
* [ ] 구현 세부사항이 포함되지 않았는가
* [ ] 상태와 연출이 구분되어 있는가
* [ ] 관계의 방향이 명확한가
* [ ] 사운드가 이벤트 단위로 정의되어 있는가
* [ ] 키와 참조 ID가 일관적인가
* [ ] Storybook 프리뷰로 검증 가능한가
* [ ] 원본 규칙 근거를 확인할 수 있는가
